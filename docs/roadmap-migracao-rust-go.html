Seção 0Sumário executivo

O sistema é um serviço HTTP de ingestão assíncrona: recebe um PDF de diário oficial via multipart/form-data, registra a importação no PostgreSQL, responde imediatamente e processa o documento em segundo plano — extraindo texto página a página com MuPDF, indexando em memória com Tantivy, e buscando as expressões cadastradas de cada perfil de cliente para gravar os "recortes" encontrados.

A tese deste plano

A migração de linguagem é o problema fácil. O problema difícil é que o comportamento observável deste serviço está codificado em detalhes semânticos de bibliotecas — o analisador léxico do Tantivy, o modo extended do motor de expressões regulares do Rust, a tabela de remoção de diacríticos, a ordem de iteração de blocos e linhas do MuPDF. Traduzir a lógica de negócio linha a linha produz um serviço que compila, sobe, responde 200 — e devolve um conjunto de recortes diferente. Em um sistema cujo produto é justamente "encontrei o nome do seu cliente na página 47 do diário", divergência é falha de produto, não detalhe técnico.

Por isso o roadmap coloca a especificação executável antes do código (F0) e a verificação de paridade como fase de primeira classe (F12), com execução sombra dos dois serviços sobre o mesmo tráfego real antes de qualquer corte. As fases intermediárias são ordenadas por dependência de risco: o que pode divergir silenciosamente vem cedo, com corpus de teste próprio, e não no fim junto com a integração.

Regra inegociável do projeto

Nenhuma funcionalidade pode ser alterada ou removida. Toda evolução técnica identificada nas fases F1–F11 entra atrás de uma chave de configuração desligada por padrão, e só é habilitada depois que a paridade estiver demonstrada com o comportamento habilitado e desabilitado. O legado é o oráculo: quando a especificação e o código Rust divergirem, o código Rust vence e a especificação é corrigida.

Seção 1Anatomia do sistema atual

1.1 · Responsabilidades e limites

O binário concentra sete responsabilidades que hoje vivem em um único arquivo, sem fronteiras internas: inicialização e configuração, exposição HTTP, autenticação, validação de entrada, persistência, extração e indexação de documento, e orquestração assíncrona. O estado global é mantido em dois lugares — o pool de conexões em um OnceLock<PgPool> acessado por função livre, e o contador de tarefas em um Arc<AtomicUsize> injetado no Depot da requisição.

1.2 · Fluxo de uma requisição

O ponto crítico do desenho: a resposta 200 OK é emitida antes do processamento. O cliente recebe "PDF carregado com sucesso" e o resultado real do recorte só é observável pela coluna status da tabela de importação — para a qual não existe endpoint de consulta.

1.6 · Encerramento e drenagem

Uma tarefa dedicada aguarda SIGINT ou SIGTERM e chama handle.stop_graceful(None). O main então aguarda o contador atômico de tarefas chegar a zero, consultando a cada 100 ms. O desenho é correto na intenção — o processo não morre com recortes pela metade — mas tem duas fragilidades: não há teto de tempo (um PDF patológico segura o encerramento indefinidamente) e a espera por sondagem em vez de notificação é desnecessária.

Seção 3As dezesseis armadilhas de paridade

Estas são as divergências que não aparecem em revisão de código nem em teste de fumaça. Cada uma produz um serviço Go que funciona perfeitamente e entrega recortes diferentes. Elas são a justificativa técnica para a estrutura deste roadmap e devem virar casos de teste nomeados em F0.

3.1 · Motor de expressões regulares

P01 — O modo x não existe em Go

O código monta format!("(?imx){}", key.replace('&', r"\s*&\s*")). A flag x (extended) faz o motor do Rust ignorar todo espaço em branco literal do padrão e tratar # como início de comentário. O motor RE2 do Go não suporta x — regexp.Compile("(?x)...") devolve erro.

A consequência é severa porque as expressões vêm do banco e contêm espaços. Para a chave ACME & FILHOS, o padrão efetivo em Rust é ACME\s*&\s*FILHOS. Uma tradução ingênua em Go produz ACME \s*&\s* FILHOS, que exige espaços literais adicionais e deixa de casar com o texto que hoje casa.

Emulação obrigatória do modo extended 
// StripExtended remove espaços não escapados e comentários '#' até o fim da
// linha, replicando o pré-processamento que a flag (?x) do crate `regex` faz.
// Espaços dentro de classes [...] são preservados, assim como \ escapado.
func StripExtended(pat string) string {
    var b strings.Builder
    b.Grow(len(pat))
    inClass, escaped := false, false
    for _, r := range pat {
        switch {
        case escaped:
            b.WriteRune(r)
            escaped = false
        case r == '\\':
            b.WriteRune(r)
            escaped = true
        case inClass:
            b.WriteRune(r)
            if r == ']' {
                inClass = false
            }
        case r == '[':
            b.WriteRune(r)
            inClass = true
        case unicode.IsSpace(r):
            // descartado — comportamento do modo extended
        case r == '#':
            return b.String() // sem quebras de linha nas expressões de perfil
        default:
            b.WriteRune(r)
        }
    }
    return b.String()
}

P02 — \w é Unicode em Rust e ASCII em Go

O padrão de junção de hífens é (?imx)(\w+)(-\n). No crate regex, \w é Unicode por padrão e casa com ção, José, ação. No RE2 do Go, \w é exatamente [0-9A-Za-z_].

Como a remoção de diacríticos acontece depois da junção de hífens, o texto ainda está acentuado nesse ponto. Traduzir literalmente faz palavras acentuadas quebradas no fim da linha deixarem de ser unidas — e uma expressão de busca que atravesse a quebra deixa de casar. Em Go o padrão precisa ser (?im)([\p{L}\p{N}_]+)(-\n).

3.2 · Analisador léxico do índice

P03 — A cadeia de análise do Tantivy tem três estágios, não dois

O campo é declarado como TEXT | STORED, o que aplica o analisador default: SimpleTokenizer (quebra em todo caractere não alfanumérico Unicode) → RemoveLongFilter (descarta termos a partir de um comprimento limite, contado em bytes) → LowerCaser. O mesmo analisador é aplicado à consulta pelo QueryParser.

O filtro de comprimento é o estágio que passa despercebido. PDFs de diário contêm rotineiramente sequências longas sem separador (códigos de autenticação, tabelas coladas, lixo de OCR), e esses termos não estão no índice. Um mecanismo Go que os indexe passa a encontrar ocorrências que o serviço atual nunca encontrou. O valor exato do limite deve ser lido do Cargo.lock da versão em produção e fixado como constante nomeada e testada.

P04 — Bytes contra runas no filtro de comprimento

O Tantivy mede o termo em bytes; os filtros equivalentes em Go costumam medir em runas. Após a remoção de diacríticos o texto é majoritariamente ASCII e os dois coincidem, mas caracteres não decomponíveis sobrevivem e criam divergência de contagem. O filtro em Go deve medir len(token) em bytes, explicitamente.

P05 — Busca de frase, não de subcadeia

A consulta é montada como "\"{key}\"" — uma frase sobre posições de termos. Isso casa JOAO SILVA, JOAO\nSILVA e JOAO, SILVA, que uma busca por subcadeia normalizada não casaria; e não casa JOAOSILVA, que a subcadeia casaria. Substituir a busca de frase por strings.Contains é o atalho mais tentador e mais errado desta migração. É obrigatório índice posicional com correspondência de sequência de termos e distância zero.

P06 — Expressão que tokeniza para vazio

Uma expressao_nm composta só de pontuação produz consulta vazia no Tantivy, que retorna zero acertos sem erro. O caminho Go precisa devolver zero acertos — não erro (que levaria a importação a −1) e não correspondência universal.

3.3 · Normalização de texto

P07 — Remoção de diacríticos não é só NFD

diacritics::remove_diacritics usa uma tabela própria. A decomposição canônica norm.NFD seguida da remoção da categoria Mn resolve a maior parte dos casos do português — á→a, ç→c, ã→a — mas não decompõe caracteres como ø, đ, ß, æ, ł, que a tabela do crate mapeia.

Nomes estrangeiros aparecem em diários. A implementação Go precisa de NFD + remoção de marcas + tabela de exceções extraída da própria crate, validada por um teste que percorra todo o plano básico multilíngue comparando as duas saídas.

P08 — A ordem das operações é significativa

A sequência é: montar a linha → trim → acrescentar \n → juntar hífens → remover diacríticos. Inverter os dois últimos passos muda o resultado, porque a junção de hífens depende de \w casar caracteres acentuados (ver P02). A ordem deve ser tratada como invariante testada, não como detalhe de implementação.

P09 — Estrutura de blocos, linhas e quebras

A montagem é literal: para cada bloco, para cada linha, os caracteres viram texto, sofrem trim e recebem \n; as linhas são acumuladas e a página é pagina.join("") — sem separador adicional entre blocos. O texto final da página tem exatamente uma quebra por linha e nenhuma fronteira entre blocos. Como a busca é de frase e a quebra de linha é separador de termos, qualquer diferença na segmentação de linhas altera quais frases atravessam quebras — e portanto quais casam.

P10 — Caracteres irrecuperáveis viram espaço

.map(|c| c.char().unwrap_or(' ')): todo caractere que o MuPDF não consegue converter vira espaço, e espaço é separador de termos. Um extrator Go que os descarte (em vez de substituir por espaço) cola termos vizinhos e cria correspondências fantasma.

3.4 · Extração do documento

P11 — Nem toda ligação Go para MuPDF expõe a mesma granularidade

O código Rust percorre text_page.blocks() → block.lines() → line.chars(). Ligações Go de alto nível costumam oferecer apenas "o texto da página", produzido por um serializador interno com regras próprias de espaçamento e quebra. Isso é próximo, não igual.

A fase F5 existe para resolver isso e tem três caminhos, nesta ordem de preferência: (a) usar a ligação existente se e somente se a comparação contra o corpus dourado for byte a byte idêntica; (b) escrever um pequeno shim em C sobre fz_stext_page que reproduza exatamente o laço, exposto por cgo; (c) manter o extrator Rust como serviço lateral durante a transição (padrão strangler fig) e substituí-lo depois. O caminho (b) é o alvo; (c) é a rede de segurança que impede F5 de bloquear todo o roadmap.

3.5 · Semântica do laço de recorte

P12 — A deduplicação é por perfil e atravessa expressões

O conjunto pages só é reiniciado quando id_perfil muda. Isso significa que, dentro de um mesmo perfil, a primeira expressão a encontrar uma página consome aquela página — as demais expressões do mesmo perfil não geram recorte para ela. Como as chaves vêm ORDER BY tp.id_perfil, tpv.expressao_nm, o resultado depende da ordem alfabética das expressões: qual expressão fica registrada em tb_recorte.expressao_busca para uma página compartilhada é determinado por essa ordenação.

Preservar isso exige manter a mesma cláusula ORDER BY, a mesma ordem de iteração e o mesmo momento de reinício do conjunto. A ordenação do banco precisa ser fixada com COLLATE explícito no plano de teste — o agrupamento é sensível à configuração regional do servidor.

P13 — O contador começa em zero e o primeiro perfil pode ser zero

let mut id_perfil: i64 = 0; — se existir um perfil com identificador 0, o conjunto de páginas não é reiniciado na primeira chave. É comportamento observável. A versão Go deve usar um sentinela explícito (*int64 nulo ou um booleano de "primeira iteração") somente se F0 confirmar que não existe perfil 0; caso contrário, reproduzir o zero literal.

P14 — Interrupção no meio deixa trabalho parcial gravado

Falha ao gravar um recorte marca a importação como −1 e retorna, abandonando as chaves restantes — mas tudo que já foi gravado permanece. Não há compensação. Isso é comportamento atual e deve ser preservado na paridade; a transação por lote de F11 muda a granularidade do que sobrevive e por isso fica atrás de chave.

3.6 · Tipos e limites

P15 — Estouros são erros, não truncamentos

i32::try_from(nr_recortes)? e i64::try_from(recorte.page)? falham em vez de truncar. Go converte silenciosamente entre tipos numéricos: int32(n) com n grande devolve lixo sem aviso. Toda conversão estreitante precisa de verificação explícita que produza erro — o que, no caso de total_recortes, leva a importação a −1 exatamente como hoje.

P16 — Datas sem fuso horário

chrono::NaiveDate não tem fuso e mapeia para date do PostgreSQL. Em Go, time.Time carrega fuso e, se construído com o local do servidor, pode deslocar um dia na gravação. Use um tipo de data puro (pgtype.Date) ou análise explícita em UTC com truncamento — e um teste com o fuso do processo forçado para algo a leste de Greenwich.

Seção 4Arquitetura alvo em Go

4.1 · Princípios de desenho

  • Portas e adaptadores. O núcleo — entidades, regras de estado e casos de uso — não importa nada de infraestrutura. Banco, PDF, índice e HTTP são adaptadores plugados na raiz de composição.
  • Injeção explícita, sem estado global. Nada de OnceLock nem de variável de pacote: dependências entram por construtor e o main monta o grafo.
  • context.Context como primeiro parâmetro. Cancelamento e prazo atravessam todas as camadas, inclusive o processamento em segundo plano — o que resolve o encerramento sem teto de tempo.
  • Erros são valores, envolvidos com %w. Erros de domínio são sentinelas verificáveis com errors.Is/errors.As; a camada HTTP é a única que traduz erro em código de status.
  • Interfaces definidas pelo consumidor. Cada porta é declarada no pacote que a usa e mantida pequena — uma a três funções.
  • Concorrência estruturada. Toda goroutine tem dono, prazo e caminho de encerramento; nenhuma é disparada e esquecida.
  • Comportamento novo nasce desligado. Cada evolução tem sua chave em configuração, com padrão que reproduz o legado.

Seção 5Método SDD e uso dos prompts

Cada fase traz um prompt pronto para execução por um agente de codificação. Eles seguem Spec-Driven Development: a especificação é o artefato primário e o código é derivado dela; quando divergem, corrige-se o código ou a especificação de forma explícita, nunca por omissão.

5.1 · Como os prompts foram construídos

  • Papel e contexto antes da tarefa. O modelo recebe o domínio, o estado do repositório e as decisões já tomadas antes de qualquer instrução imperativa.
  • Delimitação estrutural. Marcadores em XML (<contexto>, <especificacao>, <criterios_de_aceite>) separam sem ambiguidade dados de instruções — e tornam o prompt editável sem reescrita.
  • Critérios de aceite verificáveis por máquina. Cada fase termina com comandos que devem passar, não com adjetivos.
  • Antiescopo explícito. A seção <fora_de_escopo> evita a deriva mais comum: o agente "melhorar" o comportamento que precisa ficar idêntico.
  • Raciocínio antes de código. Todo prompt exige um plano ou uma tabela de decisões antes da implementação, o que expõe premissas erradas enquanto ainda são baratas.
  • Autoverificação ao final. O agente executa as checagens e relata divergências em vez de declarar sucesso.
  • Saída determinística. Caminhos de arquivo, nomes de pacote e comandos são ditados, não sugeridos.

5.2 · Protocolo de execução

  1. Execute F0 primeiro e revise a especificação humanamente. Ela é a entrada de todas as fases seguintes e o custo de um erro nela é multiplicado por catorze.
  2. Em cada fase, anexe ao prompt: docs/ESPECIFICACAO.md (saída de F0), o main.rs original e o CONTEXT.md acumulado.
  3. Uma fase por ramo, um pedido de revisão por fase. Fases marcadas como alto risco exigem revisão por segunda pessoa nos testes, não só no código.
  4. Ao fechar a fase, acrescente ao CONTEXT.md: decisões tomadas, desvios da especificação e itens adiados. Esse arquivo é a memória do projeto entre sessões.
  5. Nenhuma fase é considerada concluída com teste marcado como pendente ou pulado.

Objetivo

Transformar o comportamento implícito de 731 linhas de Rust em três artefatos explícitos: uma especificação normativa, um conjunto de invariantes testáveis e um corpus dourado de entradas reais com saídas capturadas do sistema em produção. Sem isso, "paridade" é opinião.

Entregáveis

  • docs/ESPECIFICACAO.md — contrato HTTP campo a campo, textos de erro literais, esquema de banco reconstruído com tipos, máquina de estados com todas as transições e gatilhos, e a sequência exata de normalização de texto.

  • docs/DECISOES-ABERTAS.md — perguntas que só a operação responde: existe perfil com identificador 0? qual o COLLATE do banco? qual versão exata de Tantivy e MuPDF está em produção? o defeito A13 é alcançável?

  • test/testdata/expected/ — para cada PDF: texto extraído por página (após normalização) e o conjunto de recortes gerados pelo sistema Rust, capturados por execução instrumentada.
  • Um dump anonimizado das tabelas de perfil, para reproduzir a consulta de chaves.

Critérios de aceite

  • Um binário Rust instrumentado grava as saídas esperadas e é reexecutável — o corpus é regenerável, não um artefato manual.
  • Toda mensagem de erro do serviço aparece na especificação com o texto exato, byte a byte.
  • Cada invariante INV-P* tem pelo menos um caso positivo e um negativo.
  • Nenhum item de DECISOES-ABERTAS.md permanece sem responsável e prazo.

Atenção

O corpus contém dados de diários oficiais — públicos, mas com dados pessoais. A anonimização precisa preservar as propriedades que importam (acentuação, hifenização, comprimento de termos, presença de &) enquanto substitui nomes reais. Substituição por nomes sintéticos com o mesmo perfil de caracteres, não redação por tarja.

baixo para cima: observabilidade → pool → repositórios → unidade de trabalho →

indireção, sem reflexão, sem registro dinâmico de componentes.

documentado no CONTEXT.md.

  1. sinal recebido; registra o motivo
  2. `http.Server.Shutdown` — para de aceitar, deixa terminar o que está em curso
  3. `worker.Pool.Drenar` — espera as importações em andamento
  4. fecha o pool do banco
  5. esvazia telemetria (traços e métricas)
Cada etapa respeita o prazo restante de SHUTDOWN_TIMEOUT. Com valor 0, a espera
é indefinida — que é o comportamento atual e o padrão.

Reduzido a: carregar configuração, montar, executar, traduzir erro em código de
saída. Sem lógica. Sem `log.Fatal` espalhado.

Riscos do projeto, não do software. Cada um tem gatilho observável e resposta definida antes de acontecer — a lista é revisada ao fim de cada fase.

#RiscoP × IFaseMitigação e gatilho
R1 A extração de texto não alcança paridade byte a byte. A ligação Go para MuPDF não expõe a granularidade de blocos e linhas, e o shim em C revela diferenças estruturais irredutíveis. Média × Alto F5 Caminho C (extrator Rust como serviço lateral) já desenhado e orçado. Gatilho: duas iterações completas do harness sem convergência ⇒ acionar o caminho C e seguir o roadmap.
R2 O corpus dourado não representa a variedade real. Documentos que só aparecem em fechamento de mês ou em cadernos específicos revelam divergência depois do corte. Média × Alto F0, F12 Amostragem estratificada por caderno e por mês na montagem do corpus; execução em sombra obrigatoriamente atravessando um fechamento de mês. Gatilho: qualquer divergência na sombra pausa o corte.
R3 O comportamento do analisador léxico do Tantivy é mal reproduzido. O limite de comprimento de termo ou a regra de quebra difere, alterando silenciosamente o conjunto de recortes. Média × Alto F6 Comparação de termos por página contra *.tokens.json para todo o corpus, mais teste de propriedade com um milhão de cadeias. Gatilho: impossibilidade de confirmar o limite na versão em uso ⇒ parar F6 e escalar.
R4 O esquema real diverge do inferido. Tipos, nulidade ou restrições diferentes do que as consultas sugerem quebram a gravação só em produção. Média × Médio F0, F4 Migração de linha de base que verifica o esquema real no arranque; testes de integração contra restauração de banco de produção anonimizada. Gatilho: falha de verificação no arranque impede a subida.
R5 Perda de conhecimento tácito. Quem escreveu o Rust não está disponível para responder as decisões abertas de F0. Média × Médio F0 Toda decisão aberta tem padrão provisório documentado e é resolvida por observação do sistema em produção, não por entrevista. Gatilho: pergunta sem resposta em 5 dias úteis ⇒ adotar o padrão e registrar como risco aceito.
R6 Regressão de desempenho por cgo. A travessia de fronteira Go↔C na extração custa mais do que o esperado sob concorrência. Baixa × Médio F5, F12 Medição desde a primeira versão de F5; uma travessia por documento, não por página nem por linha. Gatilho: p99 acima de 1,5× a linha de base no teste de carga.
R7 Deriva de escopo em direção a melhorias. A tentação de "consertar" o que a análise apontou durante a migração, quebrando a paridade. Alta × Médio Todas Seção <fora_de_escopo> em todos os prompts; toda evolução concentrada em F11 atrás de chave; revisão explicitamente responsável por barrar melhoria não solicitada. Gatilho: qualquer mudança de comportamento fora de chave é bloqueada na revisão.
R8 Impossibilidade de duplicar tráfego. A infraestrutura não permite espelhar requisições para a execução em sombra. Baixa × Alto F12 Alternativa: reprodução em lote a partir de um registro de requisições, com os PDFs capturados por um período. Gatilho: confirmar a viabilidade do espelhamento já em F1, não em F12.
R9 Clientes acoplados ao texto das mensagens de erro. Um consumidor faz análise da mensagem 400 e quebra com qualquer variação. Média × Médio F9 Testes de contrato byte a byte; problem+json como adição opcional, jamais como substituição. Gatilho: qualquer alteração de texto na revisão é tratada como mudança de contrato.
R10 Esgotamento de memória durante a sombra. A instância Go recebe todo o tráfego sem teto de concorrência (padrão preservado) e é morta pelo orquestrador. Média × Baixo F12 Ambiente de sombra com teto ligado e limite de memória generoso; a divergência de comportamento é conhecida e registrada. Gatilho: primeira morte por memória ⇒ recalibrar antes de continuar a contagem.

8.2 · Definição de pronto por fase

Uma fase só fecha quando todos os nove itens são verdadeiros. Não há fechamento parcial.

  1. Todos os critérios de aceite da fase verificados, com saída de comando anexada ao pedido de revisão.
  2. make lint limpo, sem supressão nova sem justificativa no código.
  3. Testes passando com -race e -shuffle=on; nenhum teste pulado, pendente ou comentado.
  4. Cobertura da fase atingida: 90% no domínio, 85% nos casos de uso, 75% nos adaptadores.
  5. Suíte de paridade acumulada continua passando — as fases anteriores não regrediram.
  6. docs/CONTEXT.md atualizado com decisões, desvios e itens adiados.
  7. Toda dependência nova justificada em uma linha.
  8. Nenhuma mudança de comportamento observável fora de chave de configuração.
  9. Revisão por segunda pessoa; nas fases de alto risco (F5, F6, F7, F12), a revisão cobre os testes com o mesmo rigor do código.

8.4 · Glossário

TermoSignificado neste documento
RecorteRegistro de que a expressão de um perfil foi encontrada em uma página de um documento. É o produto do sistema.
PerfilConjunto de expressões de busca associado a um cliente. Um cliente pode ter vários perfis; um perfil, várias expressões (variações).
CadernoSeção do diário oficial. Cada importação pertence a um caderno, e perfis são associados a cadernos.
Corpus douradoConjunto de documentos reais com as saídas capturadas do sistema atual, usado como oráculo de paridade.
Execução em sombraO novo serviço recebe cópia do tráfego real e grava em banco espelho, sem afetar produção.
ParidadeEquivalência de comportamento observável: mesmas respostas HTTP, mesmas escritas no banco, mesmas transições de estado.
SDDSpec-Driven Development: a especificação é o artefato primário e o código é derivado dela.
Chave de recursoVariável de configuração que liga ou desliga um comportamento, sempre com padrão que reproduz o legado.
